# Change log - v1.3.0

Обновлено 29 июля 2026

Новая версия агента: `1.3.0`.

Версия state: `3`.

Версия серверного IMAP-коллектора: `1.3.0`.

Главное изменение: инвентаризация теперь может попасть в Snipe-IT, даже если ноутбук не видит локальный DNS или API.

## Автономная запись в Snipe-IT

Основной путь:

```text
Snipe-IT доступен
-> агент записывает данные напрямую через API
```

Резервный путь:

```text
Snipe-IT недоступен
-> агент создаёт JSON-событие
-> подписывает его HMAC-SHA256
-> отправляет событие по SMTP
-> IMAP-коллектор получает письмо
-> коллектор записывает данные через локальный API Snipe-IT
```

Это позволяет инвентаризировать ноутбуки вне офиса без корпоративного VPN, если доступен интернет и SMTP.

JSON-вложение кодируется в Base64 и подписывается, но не шифруется. Подлинность и целостность обеспечивает HMAC-SHA256. Для HMAC используется отдельный секрет, не совпадающий с паролем SMTP.

Если SMTP временно недоступен, событие остаётся в локальной очереди и повторяется при следующих запусках, в том числе после перезагрузки.

## IMAP-коллектор

Коллектор установлен на сервере Snipe-IT.

- Запускается systemd timer каждые 2 минуты.
- Проверяет `INBOX` и папку `SnipeIT Relay`.
- Проверяет отправителя, тему, служебный заголовок, размер, JSON-схему, HMAC и `event_id`.
- Работает через локальный API Snipe-IT.
- Не требует сторонних Python-библиотек.
- Хранит результат обработки в SQLite.
- Временные ошибки API повторяет автоматически.
- Ищет relay-письма по заголовку и по теме `[SNIPEIT-RELAY]`, поскольку Яндекс IMAP не всегда корректно ищет пользовательские заголовки.

Результаты обработки:

```text
processed / duplicate / stale
-> SnipeIT Processed

повреждённое, неподписанное или некорректное событие
-> SnipeIT Rejected

временная ошибка API
-> остаётся в SnipeIT Relay и повторяется
```

`SnipeIT Processed` не обязательно означает, что письмо только что изменило актив. В эту папку также попадают:

- успешно применённые события;
- безопасно распознанные дубликаты;
- устаревшие события, которые не должны перезаписывать более свежую прямую инвентаризацию.

## Event ID и защита от дублей

Каждое relay-событие получает стабильный `event_id`.

Типы событий:

```text
install_update
owner_change
stock_checkin
daily_snapshot
```

`event_id` учитывает компьютер, серийный номер, день, тип события, поколение назначения, пользователя и состояние `assigned/stock`.

Что это даёт:

- одно логическое событие применяется только один раз;
- повторно пришедшее письмо определяется как дубликат;
- старое relay-событие не перезаписывает свежую прямую запись;
- повтор после частично выполненного API-запроса безопасно завершает операцию;
- реальная смена владельца или переход на склад создаёт новое поколение события.

## Почта без спама

Темы разделены по назначению:

```text
[PCINV-REPORT]   значимое событие для IT
[PCINV-ALERT]    проблема не исправлена автоматически за 24 часа
[SNIPEIT-RELAY]  служебное событие для коллектора
```

К `[PCINV-REPORT]` относятся:

- первая установка;
- реальное обновление агента;
- смена владельца;
- возврат актива на склад;
- ручной запуск с `-ForceEmailReport`.

Повторяющиеся DNS/curl/timeout/499 и временные ошибки API больше не создают отдельное человеческое ERROR-письмо, если relay-событие принято SMTP.

Если коллектор не сможет обработать событие в течение 24 часов, он создаст один `[PCINV-ALERT]`.

Одинаковые человеческие отчёты подавляются на 72 часа. За один запуск отправляется не более пяти старых писем из очереди.

При первом запуске `1.3.0` из очереди удаляются старые transport-error письма `1.2.x`. Смысловые ошибки, `agent_error`, смена владельца и возврат на склад сохраняются.

## Пользователь и склад

Текущий интерактивный пользователь имеет приоритет над Security log и старыми профилями.

Не могут стать владельцами:

```text
ad_*
admin
administrator
администратор
svc_*
service_*
```

Агент возвращает актив на склад, если:

- последний фактический вход выполнен под `ad_*`;
- учётная запись пользователя отключена в AD;
- поле `description` содержит `увол`, например `УВОЛ`, `уволен`, `уволенная` или `увольнение`.

Недоступность AD сама по себе не является основанием для checkin.

Если пользователь не найден в Snipe-IT, случайный checkout не выполняется. Новый актив при отсутствии корректного владельца создаётся без пользователя.

## Старые логины и Confidence

Поддерживаются:

- точные aliases из закрытого JSON;
- сохранённые aliases из state;
- старый формат `ivanovi -> i.ivanov`;
- уникальное совпадение вида `?.ivanov`.

При неоднозначности автоматический checkout запрещается.

В state и отчёт записывается confidence:

```text
100  точный JSON alias
95   точный username
90   сохранённый alias или старый формат
70   уникальное совпадение ?.surname
60   другое преобразование username
40   источник Win32_UserProfile
```

Итоговый confidence учитывает одновременно способ разрешения username и источник входа.

## Dry Run

Добавлен безопасный запуск:

```text
snipeit_dry_run.cmd
```

Dry Run читает локальные данные и Snipe-IT, но не:

- создаёт и не обновляет активы;
- выполняет checkin/checkout;
- запускает LDAP sync;
- отправляет SMTP или relay;
- меняет очередь писем;
- сохраняет `inventory-state.json`.

В логе отображается план:

```text
Would create asset...
Would update asset...
Would checkin asset...
Would checkout asset...
Would send relay event...
Reason...
Detected username...
```

## RAM

Исправлена интерпретация SMBIOS:

- `MemoryDevices=8` больше не считается восемью пользовательскими слотами;
- LPDDR/BGA определяется как распаянная память;
- MT/s подписывается как эффективная скорость передачи;
- физическая частота показывается отдельно как MHz clock;
- количество занятых слотов строится по фактически установленным модулям.

Пример:

```text
Micron Technology 16 GB LPDDR5;
current 5200 MT/s (2600 MHz clock);
rated 6400 MT/s (3200 MHz clock);
onboard
```

## Время, ОС и тег актива

Отображение времени унифицировано:

```text
Last successful inventory:  HH:mm dd.MM.yyyy
Notes Updated/Observed:      dd.MM.yyyy HH:mm:ss
```

ISO timestamp, микросекунды и `+03:00` больше не отображаются пользователю. Точное время с часовым поясом сохраняется только в state и relay payload для машинной проверки stale-событий.

Название Windows нормализуется, например:

```text
Windows 11 Pro (build 26200)
```

Повреждённая локализация вида `????` удаляется.

Агент и коллектор не отправляют `asset_tag` при создании или обновлении. Внутренний номер из 1С сохраняется при:

- обычной инвентаризации;
- смене владельца;
- checkin/checkout;
- обновлении агента;
- обработке relay.

При создании нового актива Snipe-IT сам решает, оставить тег пустым или назначить штатный автономер.

## GPO и обновление

Локальная задача `\SnipeIT\Auto Inventory` работает скрыто от `SYSTEM`.

Триггеры:

```text
запуск Windows      через 5 минут
вход пользователя   через 2 минуты
расписание          08:00, 14:00 и 20:00
random delay        до 1 часа для запусков по расписанию
```

При ошибке задача повторяется до шести раз с интервалом один час. Одновременно работает только один экземпляр.

Установщик:

- сравнивает файлы по SHA-256;
- не создаёт повторный forced-report без реального изменения;
- после первой установки или обновления выполняет один `DeploymentRun`;
- проверяет обязательные relay-поля;
- отклоняет placeholder-секреты;
- запрещает использовать SMTP-пароль как HMAC-секрет;
- останавливается, если не может защитить JSON и приватный SSH-ключ ACL.

Для `1.3.0` обязателен новый закрытый конфиг с relay-параметрами.

## Health-поля Snipe-IT

Агент обновляет:

```text
Agent version
Last successful inventory
Last error
```

По ним можно находить устаревшие агенты, компьютеры без свежей инвентаризации и машины с постоянной ошибкой.
