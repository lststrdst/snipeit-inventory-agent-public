# SnipeIT Inventory

Версия системы: `1.3.3`.

SnipeIT Inventory автоматически собирает данные Windows-компьютеров, определяет владельца, обновляет Snipe-IT, работает вне офисной сети через почтовый relay, возвращает технику отключённых сотрудников на склад и удаляет их учётные записи из рабочего списка Snipe-IT.

## Компоненты

```text
SnipeIT Inventory Agent        Windows-агент
SnipeIT Inventory Relay        IMAP-коллектор на сервере Snipe-IT
SnipeIT Inventory Maintenance  Users Deletion, cleanup и недельный отчёт
SnipeIT Inventory Weekly Report
```

Технические имена существующих файлов, каталогов и systemd units не переименовываются, чтобы обновление не создало дубли и не сломало GPO.

## Работа агента

Агент запускается скрыто от `SYSTEM`:

```text
старт Windows       через 5 минут
вход пользователя   через 2 минуты
расписание          08:00, 14:00 и 20:00
random delay        до 1 часа
```

Каждый запуск собирает имя ПК, производителя, модель, серийный номер, CPU, RAM, накопители, ОС, текущего пользователя и историю входов. Запуск задачи не означает обязательную запись в API: обычная полная синхронизация выполняется раз в сутки либо сразу при смене владельца/размещения.

Текущий интерактивный пользователь имеет приоритет над Security log и профилями. `ad_*`, `admin`, `administrator`, `svc_*`, `service_*`, `svc_inventory`, `defaultuser*`, `DefaultAccount`, `WDAGUtilityAccount`, `Guest/Гость`, `DWM-*` и `UMFD-*` не становятся владельцами. Старые логины нормализуются через alias, сохранённое соответствие и формат `фамилия+инициал`. Если после фильтрации нового владельца нет, последнее подтверждённое назначение сохраняется, а не заменяется системной учёткой.

Если пользователь найден, актив создаётся или обновляется и выполняется checkout. Если владелец изменился, агент делает checkin и checkout. Disabled-пользователь AD или административный последний вход возвращает актив на склад. Следующий обычный пользователь снова получает актив штатным checkout.

`asset_tag` не входит в payload, поэтому внутренний номер из 1С не меняется.

## Прямая и автономная запись

```text
API доступен
  -> Agent -> Snipe-IT API

API недоступен
  -> Agent -> подписанный JSON по SMTP
  -> SnipeIT Inventory Relay
  -> локальный Snipe-IT API
```

Relay проверяет отправителя, заголовки, размер, HMAC-SHA256, JSON-схему и `event_id`. SQLite не позволяет выполнить одно событие повторно. Более старое письмо не перезаписывает свежую прямую инвентаризацию.

Кратковременный ответ `NO` или разрыв соединения во время IMAP `SEARCH` повторяется до трёх раз с новым подключением. При полном сбое письмо остаётся в исходной папке и будет обработано следующим циклом, поэтому событие не теряется.

## Почта

```text
SnipeIT Inventory
  ! Weekly Reports
  Reports
  Alerts
  Warnings
  Errors
  Offline Relay
  Processed Events
  Rejected Events
```

Темы:

```text
[SNIPEIT-INVENTORY] REPORT:
[SNIPEIT-INVENTORY] ALERT:
[SNIPEIT-INVENTORY] WARNING:
[SNIPEIT-INVENTORY] ERROR:
[SNIPEIT-INVENTORY] RELAY:
```

`! Weekly Reports` содержит одно полное недельное письмо: обычный `REPORT` либо критический `ALERT`. `Reports` содержит штатные значимые отчёты агента. `Alerts` - Users Deletion и другие серверные действия. `Warnings` - безопасно завершённые операции, требующие внимания. `Errors` - ошибки агента и события, которые автоматика не исправила за 24 часа. `Offline Relay` содержит автономные JSON-события до обработки или повтора. `Processed Events` содержит применённые, повторные и безопасно устаревшие события. `Rejected Events` содержит только письма, которые подтвердились как relay, но не прошли проверку подписи, отправителя или схемы.

Коллектор сам сортирует известные темы из `INBOX` каждые 2 минуты, поэтому правила Яндекс.Почты для SnipeIT не нужны. Relay сначала ищется по служебному заголовку `X-SnipeIT-Relay: 1`, затем по широким маркерам `SNIPEIT` и `RELAY`; отчёты ищутся по `SNIPEIT-INVENTORY`, `PCINV` и `PC Inventory`. После получения письма локально проверяются точный отправитель и полный старый или новый префикс темы. Поэтому поддерживаются `[SNIPEIT-RELAY]`, `[PCINV-REPORT]`, `[PCINV-ALERT]` и старые `PC Inventory ...`, а посторонние письма остаются во входящих даже при неточном результате поиска Яндекса.

Relay `Dry Run` использует только временную SQLite in-memory: он показывает план API-действий, но не меняет Snipe-IT, письма и постоянную базу дедупликации.

### Почтовая учётная запись

Для всей системы используется служебный ящик:

```text
it@example.com
```

В Яндекс ID для него создан пароль приложения:

```text
Название: Snipeit imap collector
Тип: Почта - IMAP, POP3, SMTP
```

Пароль создаётся в управлении аккаунтом Яндекса: `Безопасность -> Пароли приложений -> Почта`. Яндекс показывает значение только при создании. Сам пароль нельзя размещать в вики, публичной GPO-шаре или публичном архиве.

Один пароль приложения используется для четырёх подключений:

```text
Agent SMTP    smtp.example.com:587, STARTTLS
Relay IMAP    imap.example.com:993, SSL/TLS
Relay SMTP    smtp.example.com:587, STARTTLS
Maintenance   SMTP через серверный закрытый конфиг
```

Где хранится значение:

```text
\\AD-SERVER\snipeit_auto_secure$\snipeit_inventory.local.json
  SmtpUser = it@example.com
  SmtpPass = <пароль приложения>
  MailFrom = it@example.com

/etc/snipeit-mail-relay/config.json
  imap_user = it@example.com
  imap_password = <тот же пароль приложения>
  smtp_user = it@example.com
  smtp_password = <тот же пароль приложения>
```

При ротации создаётся новый пароль приложения типа `Почта`, затем одновременно обновляются закрытый JSON на DC1 и серверный Relay-конфиг. После проверки IMAP и SMTP старый пароль удаляется в Яндекс ID. Поскольку пароль общий, его отзыв одновременно остановит IMAP-коллектор и SMTP-отправку агентов до обновления обоих конфигов.

## Users Deletion

Maintenance ежедневно получает disabled-пользователей из Active Directory. Для автоматического удаления недостаточно текста `увол` или OU: нужен именно флаг `disabled`, который непрерывно держится не менее 30 полных дней.

После 30-дневной выдержки и повторных подтверждений модуль возвращает hardware на склад, снимает аксессуары и лицензии, проверяет отсутствие назначений и выполняет soft delete пользователя через API. Если AD-учётку включили, отсчёт сразу сбрасывается. История Snipe-IT сохраняется.

## Weekly Report

Один раз в неделю, начиная с понедельника, приходит:

```text
[SNIPEIT-INVENTORY] REPORT: WEEKLY: <critical> critical / <overdue> overdue / <total> total
```

Отчёт показывает все ноутбуки, владельца, версию агента, последнюю успешную инвентаризацию, возраст данных, `Current/Overdue/Critical/Never` и последнюю ошибку. `Overdue` начинается с 7 дней, `Critical` - с 14 дней. За ISO-неделю в `! Weekly Reports` приходит ровно одно полное письмо: `REPORT: WEEKLY`, если критических компьютеров нет, либо `ALERT: WEEKLY`, если присутствует `Critical` или `Never`. При ошибке SMTP отправка повторяется на следующем суточном запуске, но после успеха в той же неделе не дублируется.

## Автоматическая очистка

```text
inventory-agent.log   30 дней, максимум 60 запусков
install.log           30 дней, максимум 60 запусков
локальная mail queue  30 дней, максимум 200 элементов
Processed Events      30 дней
Rejected Events       60 дней
! Weekly Reports      365 дней
Reports               180 дней
Alerts                365 дней
Warnings              180 дней
Errors                365 дней
Relay SQLite           365 дней
Maintenance SQLite     365 дней
server logs            logrotate
server update backups  90 дней
```

Рабочая папка `Offline Relay`, `INBOX`, активные кандидаты Users Deletion и неуведомлённые relay-ошибки не удаляются по возрасту.

## Что полностью автоматизировано

- установка и обновление агента через GPO;
- скрытый запуск без окна Windows Terminal;
- сбор и запись инвентаризации;
- смена владельца и возврат на склад;
- автономная доставка при недоступном API;
- дедупликация событий и повтор временных ошибок;
- Users Deletion для пользователей, disabled в AD не менее 30 дней;
- удаление старых логов, писем и записей SQLite;
- недельный контроль неотчитывающихся ноутбуков.

## Физические ограничения

Система не может получить новые данные от ноутбука, который долго не включался или не имеет доступа одновременно ни к GPO, ни к SMTP. Такой ноутбук не теряется: он появляется в Weekly Report как `Overdue` или `Never`. Отключение учётной записи в AD и восстановление физически недоступного устройства остаются внешними действиями IT.
